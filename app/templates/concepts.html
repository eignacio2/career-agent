Concept ledger

Why each layer exists

The TypeScript v1 did too many jobs at once. This rewrite is the same pipeline, cut down to the part that has to be correct: find roles, decide if they are even in-family, score them honestly for a new graduate.

You already own

SourceJob → Job → scored Job
A board returns a SourceJob. Inserting it assigns an id and makes it a Job. Scoring writes score fields onto that same row. There is no separate “Match” table — the score lives on the job because a job has one candidate.
Title pre-filter before scoring
Boards return keyword soup. Matching the body is how “Office Assistant — AI Lab Admin” looked like an agents role. The allowlist is title-only and currently keeps AI Engineer and Forward Deployed Engineer — data-science titles never pay a scoring pass.
Location pre-filter
Default keeps remote, hybrid, and on-site in any city. Unknown arrangement is kept so a missing location string is not a silent drop. Chicago-office is an opt-in. Foreign on-site still reaches the scorer and is capped at 50.
allSettled, not all
If Arbeitnow times out, Remotive and the new-grad board still count. Empty live results fall back to the sample board so the rest of the pipeline is always testable.
Caps, not penalties
A −20 penalty on a 90 still clears a 72 queue threshold. A cap of 45 cannot. Years over-reach, staff titles, and foreign on-site work use caps because they are screen-outs, not “a bit worse.”
Two-write gap (fixed here)
v1 wrote application status and job status in two statements. A crash between them desynced the tables. This slice scores and updates status in one SQLite transaction.

This slice is teaching

Test pyramid
Years extraction and caps are unit tests with no I/O. The title filter is unit tests. One pipeline test hits SQLite with the sample board. There is no Selenium suite — the expensive tests would not catch a cap bug faster than test_score.py.
Parse vs validate
httpx returns JSON as dicts (parse). Pydantic SourceJob / Profile reject malformed records (validate). Mixing those — treating a dict as a Job — is how silent None scores happen.
Transactions as a unit of work
record_score is the unit: score + verdict + status + decided_at. If that commit fails, the job stays new and the next run will score it again.

Not in this slice — on purpose

  • Resume tailoring and cover letters
  • Sending applications by email
  • PDF / LinkedIn import
  • Daily digest SMTP
  • LLM overlay on the heuristic score
  • Autopilot

Each of those is a new failure mode (prompt injection from job descriptions, ToS on ATS forms, SMTP credentials). They come back after this core is something you can debug.

Ahead

  • Schema migrations as a real tool, not CREATE TABLE IF NOT EXISTS
  • Observability: structured logs, run duration, source latency
  • Deploy: this process holds SQLite. It is not a Vercel function.
